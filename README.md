# EconAudit — 网游经济守恒审计服务

实时发现"凭空产生"的金币与物品,定位出问题的事务/环节,并追踪非法物品的后续流向。

## 核心原理

**守恒律**:除系统产出(任务奖励、NPC 商店出售)与系统消耗(NPC 回收、商店扣款)之外,
全服任一物品的总量与金币总量必须守恒。审计引擎把每个物品实例(唯一 UID)和每个账号的
金币余额都纳入台账,任何打破守恒的变动都会立即暴露。

## 三层对账(时间窗口设计)

| 层 | 窗口 | 检测目标 | 说明 |
|---|---|---|---|
| 1. 实时逐笔 | 0(事件到达即校验) | 凭空入账、无源出账、余额透支、重复事件 | 复制发生的**当次操作**即报警,亚秒级,赶在物品被洗白之前 |
| 2. 滚动窗口 | 1 分钟(可配,演示用 30s) | 窗口内 `净变动 ≠ 系统产出 − 系统消耗` | 窗口级守恒证明;窗口越短报警越快但噪音越多,1 分钟是延迟与聚合效果的折中 |
| 3. 周期快照 | 每次登录/重连 + 每 5 分钟全量 | 服务器**漏报事件**造成的盲区(静默回滚等) | 快照与台账双向核对:多出来的(幽灵物品/一物两主)和少掉的(凭空消失)都抓 |

为什么需要第 3 层:前两层只能审计"服务器如实上报的事件"。如果某条代码路径
(典型的如断线重连的状态恢复)没有接入事件总线,物品凭空多了却没有任何事件,
只有拿服务器真实状态与台账对账才能发现。快照周期决定了这类盲区的最大存活时间。

## 检测能力

- **定位**:每条异常携带 `TxnId`(事务)、`OpId`(操作,如 `mail-claim#16`)、`Channel`
  (trade/mail/auction/reconnect/snapshot),直接回答"哪次操作、哪个环节"。
- **追踪**:每个物品 UID 的完整流转轨迹(谁→谁、何时、哪次操作);被污染物品
  流经的所有账号自动汇总;黑金(凭空产生的金币)随转账在账号间传播记账。
- **幂等**:按 `EventId` 去重,事件重复投递不会产生误报;ID 相同内容不同本身即异常。
- **双向守恒**:既抓"多出来"(复制),也抓"没了"(物品凭空消失)。

## 项目结构

```
src/EconAudit.Core/   审计引擎(无依赖的类库,可直接接入真实服务器)
  Events.cs             FlowEvent / Anomaly 模型
  AuditEngine.cs        实时校验 + 滚动窗口 + 快照对账 + 污染追踪
src/GameSim/          带 4 处复制漏洞的演示服务器 + 场景驱动
  GameServer.cs         简化游戏服务器(交易/邮件/拍卖/仓库/断线重连)
  Program.cs            演示场景:先跑正常业务(验证零误报),再逐一触发漏洞
```

## 运行

```bash
dotnet run --project src/GameSim
```

## 演示服务器内置的漏洞(均为真实网游复制漏洞的简化模型)

1. **交易 × 断线回滚竞争**(`TradeWithDisconnectRace`):交易交付后卖家断线,
   断线保护线程用交易前快照回滚卖家背包 → 双方各持一份。
2. **邮件重复领取**(`MailClaim`):发货与"标记已领取"非原子,可重复领取同一附件。
3. **拍卖已售出仍可取消**(`AuctionCancelBuggy`):取消未校验成交状态,
   买家已拿到货,卖家又收到退回。
4. **重连加载过期快照且漏报事件**(`ReconnectRestoreSilent`):重连用登录时的
   旧快照整体覆盖当前状态,且恢复路径没接事件总线 —— 实时层完全看不到,
   只能被第 3 层快照对账抓获(同时造成金币回滚和已存仓库物品复活)。

## 接入真实服务器

1. 在服务器所有改变物品/金币归属的代码路径上 Emit `FlowEvent`
   (建议经消息队列异步投递,`EventId` 用全局唯一 ID 保证幂等)。
2. 邮件、拍卖行、公会仓库等容器要作为"持有者"参与记账(挂单=转给容器)。
3. 系统产出/消耗走 `FlowChannel.System`,其余渠道一律按守恒校验。
4. 登录、重连、定时任务触发 `ReconcileSnapshot` 上报全量状态。
5. 消费 `AuditEngine.Anomalies`(实时告警)与 `Windows`(窗口证明)接入告警平台。
